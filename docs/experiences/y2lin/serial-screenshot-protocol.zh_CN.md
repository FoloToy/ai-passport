# 实现 FAP_SCREENSHOT_V1 串口截屏协议

把 **音量小哨兵** 环境噪音计发布到 AI Passport 社区市场后沉淀。publisher
工作流要求通过 `FAP_SCREENSHOT_V1` 串口协议现场截取设备屏幕，本条记录在
ESP32-C3 + LVGL 9.5 上实现该协议踩过的坑（对应提交 `6acfd9d` 至 `cc1d72f`）。

协议本身很小：主机经 USB-CDC 发送 ASCII 行 `FAP_SCREENSHOT_V1\n`，设备回
`FAP_SCREENSHOT_V1 <宽> <高> RGB565LE <字节数>\n` 头行，再紧跟恰好
`<字节数>` 字节的小端 RGB565 像素。下面的坑全部出在设备侧管线，而不是协议。

## 读取任何数据前，先安装 USB-Serial-JTAG 驱动

直接进入应用界面的单应用固件不启动 REPL，控制台日志又走 VFS 寄存器直写
通道，于是整个系统没有任何人安装过 USB-Serial-JTAG 驱动。此时调用
`usb_serial_jtag_read_bytes()` 会解引用空的驱动对象——在本板上表现为反复
崩溃重启；由于背光已经点亮，用户看到的是“屏幕一直闪”，而不是串口报错。要
显式安装驱动（缓冲不必大：rx 256 字节、tx 1024 字节足够），调用
`usb_serial_jtag_vfs_use_driver()` 把控制台 VFS 切到驱动通道，并让读取任务
低频轮询 `usb_serial_jtag_is_driver_installed()`，而不是假设驱动就绪。

## 串口读取任务绝不能忙等空转

`usb_serial_jtag_read_bytes()` 持续返回错误时，紧凑的读循环会打满任务、
饿死空闲任务并触发任务看门狗——设备反复重启，表现同样是“屏幕在闪”。读错误
要退避（200 ms），任务优先级要压到 LVGL 之下（LVGL 为 4，串口辅助任务取 3），
每条“无事可做”的路径都要有 `vTaskDelay()`。本板的闪屏有两个独立成因（空
驱动指针和忙等空转），两类都要修，不能只修一个。

## 按子串匹配命令，不要依赖换行终结

Windows 终端工具可能吞掉行尾换行，严格的换行终结行匹配永远不会命中，设备
毫无反应、主机只能超时。改用“最近命令长度字节”的滑动窗口去匹配 ASCII 命令，
遇到任何行终结符就重置窗口，命中后清空窗口，避免残留字节连续误触发截屏。

## 快照渲染写入静态预留的缓冲

先说两个 LVGL 9.5 的事实：不设 `CONFIG_LV_USE_SNAPSHOT=y` 时快照辅助函数
整体不可用（隐式声明编译错误是第一症状）；`lv_snapshot_take()` 返回的是
`lv_draw_buf_t*`，旧示例里的 `lv_image_dsc_t*` 写法已经编译不过。

真正的坑在堆上：运行时堆明明还有约 220 KB 空闲，却在 LVGL、codec 栈和 DMA
跑起来之后拿不出一块连续的 153,600 字节（240x320x2）；动态分配每次都失败，
而空闲堆日志看起来完全健康。要在编译期静态预留整屏 RGB565 缓冲（64 字节
对齐），用 `lv_draw_buf_init()` 初始化描述符，再用
`lv_snapshot_take_to_draw_buf()` 渲染——这是官方的外部缓冲模式，完全不经过
LVGL 堆。LVGL 锁只覆盖渲染瞬间（`bsp_lvgl_lock()` / `bsp_lvgl_unlock()`），
回传期间 UI 照常动画；任务栈要留余量：整屏软件渲染配 8192 字节很宽裕。

## 载荷按发送环形缓冲的容量分块流式发送

`usb_serial_jtag_write_bytes()` 底层落在 `xRingbufferSend()` 上，而它对超过
环形缓冲容量的整块写入会立即失败（"data will never ever fit"）。把 153,600
字节载荷一次性提交等于一个字节都发不出去，主机报“数据在声明长度之前就结束”。
按 512 字节分块（远小于 1024 字节的 tx 缓冲）流式发送，每块带充足超时阻塞；
某块失败（主机拔线）就放弃本次传输，但任务继续存活等下一条命令。

## 二进制窗口期间静默一切日志

ESP-IDF 的日志行与应答共用同一条 USB-CDC 流，而主机按声明的字节数精确读取，
混入任何一个日志字节都会让整幅图像错位。在发出第一个头行字节之前
`esp_log_level_set("*", ESP_LOG_NONE)`，在最后一个像素字节之后恢复默认级别，
传输完成后的日志严格留在这个窗口之外。

## 命令保持只读语义，失败就静默

publisher 的契约是纯观察：命令不重启、不刷机、不改设置。任何失败（锁超时、
快照不符、驱动消失）都只记日志、不应答——主机会得到一个干净的超时错误，而
不是一条被破坏的流。应答前还要防御性核对快照确实是紧排整屏 RGB565。

## 对下一个应用的泛化

- 任何要读 USB 串口控制台的代码，都要先确认驱动已安装；不启动 REPL 的固件
  只能靠应用自己装。
- 先用裸串口终端（开本地回显）调试管道，再调试协议——这能区分“命令没到”
  和“设备没答”。
- 串口载荷写入尺寸要对着发送环形缓冲规划，而不是对着载荷本身。
- 整屏帧缓冲静态预留；无 PSRAM 的芯片上，运行时碎片让 150 KB 连续分配
  不可依赖。
- 二进制应答与日志输出在时间上互斥。
- 看到“屏幕在闪”先按崩溃循环处理、读串口日志，再考虑动显示代码。
