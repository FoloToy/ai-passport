# 常连 BLE 链路下的空闲省电

经验来自 **随身对讲机**：蓝牙链路就是这个产品本身，所以设备既要把闲置功耗压下来，又一步都不能把链路弄丢。真正有用的手段最后是三件事——常规的 DFS、音频 codec 挂起、以及一条不太直观的"什么才算活动"的判据；而第三条决定了"省电策略写了"和"省电策略真的生效"之间的差别。

## 链路在用时，不要开系统浅睡

`CONFIG_PM_ENABLE` 配合动态调频是安全的：设备一闲下来 CPU 就落到 40 MHz 的底频，链路照旧。但按上游 Low Power demo 的做法往 `esp_pm_configure()` 里加 `light_sleep_enable = true` 就不行：BLE 连接活跃时链路会断开，手机会报 GATT 监督超时（`status=8`）然后重连。这个现象稳定可复现，所以本产品只用 DFS 降频。控制器自己的 modem sleep（`CONFIG_BT_CTRL_MODEM_SLEEP`）可以留——它不会拖住链路。

这类设备的实用准则：**只要链路就是产品，任何可能推迟射频监督响应的电源状态就不在选项里。**

## 只把真正的流量算作"活动"

手机在连接期间会以 1 Hz 持续发控制帧。第一版实现把"收到任何 BLE 包"都当作活动，于是设备永远不觉得自己空闲、永远进不了低功耗状态——省电只存在于日志文案里。现在只把用户能感知的帧算作活动：**下行音频与上屏文本**。改完以后空闲切换按时触发，并且稳定。

## 空闲时挂起音频 codec，有活动立刻唤醒

越过空闲门限后，固件执行
[Shutting Down On-Board Peripherals Before Deep-Sleep](deep-sleep-peripheral-power-off.zh_CN.md)
里验证过的 ES8311 挂起序列并记录回读结果；第一次真实活动再把它唤醒。唤醒路径必须在下一句的第一帧需要播放**之前**跑完，而不是等帧到了才醒。反复多轮实测：每一轮都是"解码帧数 = 接收帧数、丢弃 0、剩余 0"。

## 熄灭背光 ≠ 关掉面板控制器

亮度调到 0 只是**看不见**：控制器仍在把帧存持续扫描到玻璃上，而**这个扫描（不是帧存本身）**才是设备闲置时的那部分电流。`esp_lcd_panel_disp_on_off(panel, false)`（DISPOFF）停掉刷新、但**保留帧存**，于是闲置路径可以关掉面板，而唤醒路径能**立刻**恢复画面、不需要重绘。

两个值得照抄的细节：

- **可逆的那条路要和终止式的分开。** 运行期熄屏只用 DISPOFF/DISPON；SLEEP IN 留在深睡准备函数里 —— 那是扇单向门（它连背光 PWM 都停，而设备本就要重启）。DISPOFF 撤销不要钱；SLEEP IN 需要 ~120 ms 的 SLPOUT 序列，而它是否能带着帧存一起睡醒，手册说得不够明确，不适合放在产品路径上赌。
- **唤醒的顺序要对：先面板、后背光。** 面板还没开就把背光点起来，会先闪出一帧没就绪的画面。

保留画面是这笔交易里**便宜的那一半**，所以"瞬间唤醒"几乎不要钱。和这块板子上的一切一样：要报数字就用仪器实测 —— 板上电量计只给 SOC 与电压。

## 深睡是另一步、也是更靠后的一步

只有前面几步都成立，深睡才有意义；而它需要
[Landscape Rotation and a Deep-sleep Key Wake](landscape-rotation-and-deep-sleep-key-wake.zh_CN.md)
里那条按键垫交接（否则 ADC 占着引脚会让低电平按键唤醒在入睡瞬间就成立）。两条规则让它不再反复：

- **按键被按住时拒绝入睡**，过一会重试——而不是"睡下去又立刻醒"地循环。
- **用交接后的引脚电平作证**："代码跑了"不等于引脚读回了正确的电平，必须把电平打进日志。

## 判据看链路，不要看串口日志

深睡中的设备会关掉 USB 串口，采集自然断掉（这是设计使然）。更麻烦的是：设备只要重启一次，USB 口重新枚举，**已经在跑的采集会悄悄收不到数据，却看起来一切正常**。这两件事都让"日志没有新行"变成很差的判据。要回答"它到底睡住了没有、回来了没有"，看**对端（手机）的连接流**（连接 / 断开的记录）。

## 用设备自己报的数对账

播放路径会为每一句打印计数：收到多少帧、解了多少、丢了多少、结尾还剩多少在队列里。**结尾"还剩 23 帧"** 这一条读数，直接暴露了一个真 bug——句子在仍有解码队列积压时被空闲超时判定为"播完"，于是长回复被截断。设备自己报数，把"语音有时会断"这种模糊反馈变成了可复现、可修复的缺陷。
