# 设备端对弈 AI 的墙钟预算

经验来自 **四子棋** 的发布：它的电脑对手要在无 PSRAM 的 ESP32-C3 上搜索 10 × 7 棋盘。

## 不要用节点数给搜索限时

最初版本用一个固定节点数上限。在设备上实测，150,000 个节点耗时约 11 秒——大约每秒 1.5 万节点，比桌面估算慢一个数量级，因为这是单发射 RISC-V 核、代码还在 flash 缓存里跑。同时它把空闲任务饿住的时间足够触发看门狗。

修法是改成**墙钟限时**并让深度自适应：从深度 2 起迭代加深，永远保留一层完整结果为答案，每步预算约半秒。在这块板上大约对应 8k–12k 节点，已经是像样的休闲对手；换成更快或更慢的板子会自动搜得更深或更浅，而不是卡死。

## 让出 CPU，并选合适的检查粒度

优先级高于 idle 的 CPU 密集任务连续跑几秒就会触发任务看门狗，所以搜索每 N 个节点回调一次平台层：`vTaskDelay(1)` 让空闲任务运行，同时比较当前时间与截止时刻；返回 false 即放弃本层，沿用上一次完整结果。

N 应该按实测节点速率来定，而不是凭感觉：这里 4,096 个节点约等于 270ms 超调，于是改成 1,024 个节点（约 70ms 超调，让出带来的开销不到 2%）。

## 搜索层不依赖平台，难度做成产品决策

搜索本身不依赖 ESP-IDF：时间预算、时钟、让出动作都通过 options 结构注入，因此这个模块可以跑宿主测试——单元测试用关闭预算的确定性搜索断言“一步取胜”“必堵”，并跑完整自对弈。

难度用**失误率**表达，而不是降低搜索深度。浅层搜索并不会下得更弱，它只是看不见威胁，看起来像坏了；在“必胜/必堵”判断之前按固定概率随机走一步，既能造出明显打得赢的对手，又仍会惩罚明显失误。

模型、几何、菜单状态机与搜索都有宿主测试覆盖；设备上每步约半秒，感觉是“在思考”而不是“在卡”。
