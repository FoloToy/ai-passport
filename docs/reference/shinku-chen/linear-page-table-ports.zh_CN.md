# 源工程是「线性页表」的作品怎么移植

有几部小米手环视觉小说移植版是把整部作品压成**一条全局页表 + 一份分支配置**，而不是一个场景
一个剧本文件。《DRACU-RIOT!》就是这一类：52,787 页、54 处选项页，外加一份
`branchConfig.js`，把所有"偏离线性"的地方都记在里面（前进特判、回退堵死、条件路由、结局页）。
移植这类源工程，主要工作量在数据侧，阅读器本身很小。

## 源工程给了什么

- **一条全局页表**：读一页就是"页号 + 1"，除非某张表说不是；选项直接存目标页号。
- **一份 JavaScript 的分支配置**：条件路由是对选择历史求值的闭包，例如
  `(choice) => { if (choice[3113] === 2) return 3912; return 3871; }`。
- **其余都是美术和文本**，而且已经按手环屏幕尺寸转换过。

## 可用的管线

1. **把分支闭包编译成数据，而不是代码。** 打包时把那个 JS 子集解析成「有序规则 = 字面量合取
   → 目标」+ 兜底，并**穷举校核**：对每条依赖的选项页取全部组合，与原始表达式的结果逐条比对。
   固件侧因此不需要表达式求值器，只要几个小表的查表 + 一个选择历史数组。注意唯一一处
   `if (!(...))` 写法：按 if 链语义交换分支，就能保持"只有正向字面量"，不必展开补集。
2. **页表与正文分成两路块流**，共用一小块解块缓冲，并让这块缓冲**单一所有者**（见同一目录下的
   共用缓冲条目）。正文存成「按字频排序的字符表 + 2 字节下标」，顺便把字库的字形顺序也定下来。
3. **页表块按固定页数切**（例如 256 页 = 4 KB 原始字节），页号定位就是算术，不用搜索。
4. **章节表按页号排序。** 上游的章节表是按路线分组的，"下一章"要靠页序而不是作者顺序；再把
   源工程列出的后日谈入口一并并进去，列表才和作品实际内容一致。
5. **用宿主机走线验证，而不是截图。** 确定性走线（"永远选第一项" + 带真实选择历史 BFS 搜每条线
   的入口页）能抓到路线死循环和不可达章节，单帧抓图永远看不出来。

## 发布前值得专门检查的数据缺陷

- **回跳落在重复场景块里。** 转换器可能把同一段场景输出两份，而把两个变体的收场都导回**第一份**，
  于是玩家会在几百页里无限循环，任何选项都出不去。检查方法：把前进图当成函数图，问"每个可达
  页面是否仍然能走到结局"；这条检查应该进打包测试。
- **路线入口可达性。** 断言每条线的入口页都能靠真实选择历史从第 1 页走到；条件推导错一处，
  玩家就会静默走进普通结局。
- **章节与后日谈条目**要为每条线都存在。

## 可复现性

把源工程的**素材与剧本数据**（不是它的快应用代码）提交进 fork，把打包器的默认 `--source`
指向这份拷贝，并在旁边写下精确的打包参数 —— 这样 clone 下来就能重建出逐字节一致的包，
不需要联网；"去掉这个文件 / 改这个画质"这类实验也才便宜可重复。

可复现性不能盖过授权。任何源工程内容入库之前，先过一道再分发门槛：

- **先核对许可、拿到允许。** 权利是分开的：美术归原作公司，译文归汉化组，移植本身归移植
  作者；署名或"个人学习"声明都不构成再分发授权。每一项素材、剧本与译文入库前，都要确认
  许可条款，或取得明确许可。
- **拿不到授权的输入不要入库。** 不能再分发的输入就不提交，哪怕是为了可复现性；改为记录
  "由用户自备输入"的导入/转换流程 —— 读者自己提供那份输入，由打包器在本地转换。
- **入了库的要记录来源与范围。** 每个提交进仓库的输入，都在打包参数旁写明：来自哪里、
  依据哪份许可或授权、允许哪种范围的再分发。

逐字节可复现很有价值，但不能靠"建议把有版权的第三方内容未经授权地提交进仓库"来实现。
