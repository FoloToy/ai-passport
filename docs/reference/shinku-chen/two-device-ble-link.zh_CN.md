# 无 PSRAM 的 AI Passport 双机 BLE 联机

这些结论来自 **Connect Four（四子棋）** 双机联机功能在两台真机上的验证（2026-09-18）。属于通用、对上游也有价值的经验：任何想让两台 AI Passport 不经过手机互相通信的应用都用得上。

> **验证状态。** 在两台运行同一固件的真机上实测。角色、握手、完整对局、再来一局与对端离开都跑过；下面的堆数字来自设备日志，不是估算。距离、长时间运行、三台以上同场、续航数据**未覆盖**。

## 对等发现：把角色选择从界面里去掉

不需要告诉任何一台设备"你是主机"。两边**同时**广播自定义 GATT 服务、又同时扫描对端的广播名，然后自行决定谁去连接：

- 把对端的广播地址与本机地址逐字节比较：**地址大的一方主动连接**，另一方等待。这条规则是反对称的，两台设备各自算出的结果必然相反，既不需要协商，也不会出现双方同时连对方。界面上因此不需要"主机 / 加入"这个选项。
- 用名字前缀（如 `C4-` + MAC 后两字节）做发现过滤，比在广播数据里匹配 128 位 UUID 简单，还顺便让两台设备在扫描列表里可区分。UUID 仍应放进扫描响应，方便手机和通用 BLE 工具识别这个服务。
- 128 位 UUID 沿用 Nordic UART 布局（`6e400001`/`6e400002`/`6e400003-b5a3-f393-e0a9-e50e24dcca9e`），这是"通用 BLE 工具或手机也能当对端"的前提。NimBLE 的发现日志会打印服务 UUID，是快速确认两边布局一致的办法。
- 连接建立后停止广播；断开后同时重启广播与扫描，这样不用重启就能重连。

`CONFIG_BT_NIMBLE_MAX_CONNECTIONS=1` 对 1:1 对战是正确设置，但也意味着上面那条规则必须严格：同时扫描又接受连接的多角色设备，否则可能撞进"连接竞争"。

### 在 sdkconfig 里打开四个角色

这条链路需要 **peripheral + broadcaster**（广播自己）与 **central + observer**（扫描对端并主动连接）。模板为了给示例瘦身，默认写了 `CONFIG_BT_NIMBLE_ROLE_CENTRAL=n` 与 `CONFIG_BT_NIMBLE_ROLE_OBSERVER=n`；只要有一个没打开，设备就会**静默地**既发现不了对端也连不上（对应的 GAP 过程直接失败）。把四个角色都打开（它们只在链路启动时才实际占用资源），并保持 `CONFIG_BT_NIMBLE_MAX_CONNECTIONS=1` 用于 1:1 对战。

## 先算内存，再定功能集

在已经跑起游戏界面、音频任务和 LVGL 的 ESP32-C3 板子（无 PSRAM）上实测：

| 时点 | 空闲堆 |
| --- | --- |
| 开机、应用界面就绪后 | ~191.9 KB |
| 调 `nimble_port_init()` 之前 | ~131.2 KB |
| 已连接、链路稳态 | ~125.2–128.9 KB |
| 链路停止、host 任务拆掉之后 | ~192.0 KB |

也就是说：链路**启动约需 60KB 堆**，连接期间再占约 6KB，停掉后完整归还。这正是本项目把链路做成"进入联机模式才启动"而不是开机就启动的原因。

与之相关的一个坑是**静态**整屏截图缓冲：320 × 240 RGB565 一帧是 150KB，而开机时最大连续空闲块实测只有约 114KB，所以那块缓冲只能放在 `.bss`，等于永久占 150KB。在这块板子上 BLE 与它无法共存：

- 老实测出来这个数字，才能决定出厂配置。本项目出厂固件带联机，串口截图退成可选构建（`-DC4_ENABLE_SCREENSHOT=ON`），且截图构建下会明确显示 `BLE UNAVAILABLE`，而不是以难以理解的方式失败。
- 如果确实既要截图又要联机，必须在设计阶段就想办法（例如分条渲染到小块缓冲），这不是一个配置开关能解决的。

## 只在真机上才会暴露的两个 NimBLE 坑

这两个都编译通过，是靠设备日志才定位的：

1. **每个 characteristic 都必须有 `access_cb`，哪怕只用 NOTIFY。** `ble_gatts_chr_is_sane()` 会拒绝 `access_cb` 为 NULL 的特征，随后整个服务注册以一个笼统的 `ble_gatts_count_resources rc=3`（`BLE_HS_EINVAL`）失败。当时堆很充裕（空闲 195KB），所以这个错误极易被误读成"内存不够"。给通知特征补一个读取回调（顺便返回两个识别字节，方便手机端调试），并在本地加一条自检，明确指出是哪一条特征缺回调。
2. **描述符发现的 `EDONE` 在订阅写成功之后也会到来。** central 侧的描述符发现回调最后会收到 `error->status == BLE_HS_EDONE`。它**不等于**"没找到 CCCD"：在已经找到 CCCD、并已发出订阅写之后，同样会收到它。把它当成失败会表现为"连上 → 订阅 → 立刻自断"的死循环（抓到的日志里循环了 19 次）。正确做法是用一个"已找到 CCCD"的标志位区分，只有真的没找到才算失败。

## 射频之前先初始化 NVS

没有 `nvs_flash_init()` 时，控制器/PHY 读不到射频校准数据，每次启动都要做全量校准：

```text
E phy_init: esp_phy_load_cal_data_from_nvs: NVS has not been initialized.
W phy_init: failed to load RF calibration data (0x1101), falling back to full calibration
```

加上 `nvs_flash_init()`（**不要**顺手擦除，避免毁掉应用数据）之后：第一次启动链路会打印 `phy_init: Saving new calibration data ...`，而**下一次**启动 `phy_init` 完全不再输出——这就是"校准数据被复用"的直接证据。即使 NimBLE host 侧配了 `CONFIG_BT_NIMBLE_NVS_PERSIST=n`，BT/PHY 这条路仍然需要 NVS。

## 可靠投递放在应用层，而不是指望 BLE

两个方向都没有应用级确认：peripheral 侧是通知，central 侧为了延迟可以用无响应写。对回合制游戏来说，丢一个包不是丢一帧画面，而是两块棋盘永久不一致，所以必须自己加一层：

- 帧格式：magic + 版本 + 类型 + `bit7=带数据` 与 7 位序号 + `bit7=ack 有效` 与最近接受的对端序号 + 最多 3 字节负载。一帧在默认 ATT MTU 下绰绰有余，而且线上尺寸很好确认（3 字节负载时日志是 `write ... len=8`，纯确认帧是 `len=5`）。
- 停等：只接受"期望的下一个序号"，重复包只重发确认不重复交付，每 400ms 重传、5 次之后明确进入"对端丢了"状态。
- 负载里带本手之后的落子总数并在收到时校验，这样失步会被发现，而不是悄悄出现两块不同的棋盘。
- 先手由连接角色 + 共享的局号决定（例如"central 先手、逐局交替"），两台设备无需额外往返就能算出同一答案。两边都可能提出下一局号时按 `max()` 收敛——两边都采用对端值会互相交换，导致颜色错位。
- 这一层放在纯 C 模块里并配宿主测试；BLE 只当字节管道。

## 收尾与休眠

在 `esp_deep_sleep_start()` 之前先停射频（`nimble_port_stop()` + `nimble_port_deinit()`，再删掉 host 任务），否则射频会一直带电。停链路同时也会把约 60KB 还给堆。对端会看到断开，所以给它一个"对端离开"且继续搜索的界面——并且不要让空闲休眠计时器在联机对局中途触发。

## 怎么测

- 真机验收需要两台板子；最有用的证据是两边串口日志：主动方打印 `role=central`，另一方 `role=peripheral`，并且两边打印同一个局号、颜色相反。
- 迭代协议时，用 PC 端 BLE 对端（Python + `bleak`）可以省掉第二台板子：以 central 身份连上正在广播的板子、说同一套帧、按规则应招落子，因此只用一台板子就能打完整局。那套对端工具（`tools/c4_peer.py`）跟着两机 BLE 传输层走，不放在本说明里。
