# 烧写合并镜像对已存数据做了什么

本条目来自 **《飞鸟会长不肯认输》**（Asunabi）的真机验收：同一个镜像、同一块板子，对
「这样烧会不会清掉设备数据」给出了两个不同的答案 —— 而答案取决于用的是哪一种烧写方式。

## 合并镜像在没有内容要写的地方是 0xFF

交付产物是从 0x0 整片烧写的 merged 镜像。默认分区表里 NVS 在 `0x9000`（24 KiB），
`phy_init` 在 `0xF000`（4 KiB）。在这个 7,917,142 字节的镜像里，这两个区间全是 `0xFF`——
`merge-bin` 会把引导区、分区表、应用与数据分区之间的空隙用 0xFF 补齐。

这些 `0xFF` 只是填充，不是保留数据的承诺。merged 镜像从 `0x0` 写入，覆盖它包含的整段
地址范围；写入工具会擦写这份文件触及的每一个扇区，NVS 与 `phy_init` 都在其中。仓库的
烧写策略也是这么写的：merged 文件会把各镜像之间的空隙一并补齐，因此整片烧写可能重置
NVS 与 PHY 数据区。

## 分段烧写与整片烧写是两种不同的操作

同一个镜像、同一块板子，相隔几分钟烧了两次：

- 第一次烧完启动，应用日志显示它从 NVS **恢复**了存档（续读点是第 10 章）。
- 第二次烧完启动，同一份固件却显示**没有存档**，改用默认值。

两次都没有损坏，也没有写失败，但两次结果不一致。这个不一致本身就是结论：整片烧写不能
被描述成"会保留已存数据"，烧完能正常启动也不能当作数据被保留的证据。

- **分段烧写**（`idf.py flash`，或按分区表配置的偏移逐段写）可以在分区表一致、目标地址
  不覆盖数据区的前提下，让没有写到的数据区扇区保持不变。正常开发中需要保留现有 NVS 状态
  时，用的就是这种烧法。
- **整片烧写 merged 镜像**覆盖这份文件的整段地址范围，包含 NVS 与 `phy_init`，可能重置这
  两个区域。它适合空设备首次烧写或有意做一次完整刷新；不要承诺这样烧完 NVS 等已存用户
  数据还在。

## 那应该怎么做

- **要保留数据**：先用应用支持的方式把数据导出或另存，再用分段烧写，并确认分区表兼容、
  写入目标不覆盖数据区；不要盲目整片烧写 merged 镜像。
- **要清空数据**：显式地做，并说明做了哪一种 —— 应用自己擦掉自己的命名空间，或对该分区
  显式 `erase_region`。不要依赖整片写来当擦除。
- **汇报真机测试时，写明用的是哪种烧写方式、哪些数据被保留了**，而不是默认某一种结果：
  启动日志通常会告诉你，例如"恢复了存档"或"使用默认值"。
- **验收发布时要烧已发布的产物**，而不是本地构建；这个习惯已经记在
  [静态缓冲按面板算，并验证已发布的产物](release-artifact-verification.zh_CN.md) 里。
