# 资源包字段漂移：要让它响亮地失败

这篇经验来自发布《星空列车与白的旅行》阅读器的过程。
应用从一个二进制资源包里读剧本、背景与立绘，包由 Python 打包器生成，C 侧按固定偏移解析。
有一次给某种记录加了字段：打包器写了，解析器从来没读。结果不崩、构建全绿、宿主测试全过，
而产品以一种"看似合理"的方式错了很久。这篇记录事情本身，以及能提前抓住它的三个习惯。

## 发生了什么

- 立绘记录（`SEC_FG`）从 24 字节长到 26 字节：`color_offset`、`color_len`、`mask_offset`、
  `mask_len`（四个 `uint32`），然后是 `w`、`h`、`x`、`y`、`owner`（五个 `uint16`）。
  打包器写入了 `owner` —— 这张立绘归属的角色，由"哪个有名字的说话人引用了它"统计得出。
- C 解析器读到 `y`（偏移 22）就返回了。`owner` 保留函数开头 `memset` 留下的 0，
  静默地表示"name 表第 0 项"。
- 界面规则是"立绘只在该角色本人说话时出现"。所有立绘都归到第 0 项之后，规则退化成
  "只有主角说话时才有立绘" —— 11777 个对白步里只有 1005 步（而不是 3444 步），
  另外六个角色再也不会出现。它看起来像"规则太严"，不像 bug。

## 为什么测试没抓住

- 宿主测试断言的是**计数** —— `sprite_steps > 800` —— 而 1005 通过。这个阈值是按错误
  行为标定的。
- 它还断言"画出的立绘，其归属等于当前说话人"，而当所有归属都是同一个下标时，这当然成立。
- Python 侧测试解析资源包文件，验证了 owner 字段存在且下标合法 —— 它检查的是**生产侧**，
  不是**消费侧**。
- 没有任何测试比较"两侧对同一条记录看到的东西"。

## 能抓住这类 bug 的三个习惯

1. **断言分布，而不是计数。** "画出来的立绘至少覆盖 5 个不同归属"在解析漂移时（只有 1 个）
   必挂，在修好之后（7 个）通过。计数衡量"发生了多少"，分布衡量"数据是否还保有它的多样性"。
2. **同一条真实记录，两侧各 dump 一次。** 一段五行脚本：Python 打印第 n 条记录的解析字段，
   C 侧解析同样的字节再打印同样的字段 —— 漂移几秒内暴露。维护成本极低，还能抓到文件级测试
   看不到的布局错误。
3. **让生产侧也断言不变量。** 打包器手里有引用统计，可以在数据退化时（例如"超过一半立绘共用
   同一个归属"）直接让构建失败，而不是把这份沉默留给运行时规则。

保持**只有一份偏移表事实来源**（记录长度常量紧挨着打包器的格式串，解析器按同样顺序写注释），
并且每次**追加字段时重读一遍解析器** —— 追加恰恰是编译器和格式检查都看不见的那种改动。
