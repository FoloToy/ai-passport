# 从 LVGL 刷屏路径抓真机画面

这篇经验来自发布《星空列车与白的旅行》阅读器的过程。
视觉小说移植必须逐页核对 —— 正文带、名牌、立绘站位、章节标签、电量 —— 拿手机拍一块 240 × 320 的
屏幕远远比不上像素本身。这块板子没有 PSRAM，界面本身已经用一块整屏画布放画面，再拿 150KB
出来做截图缓冲不现实。办法是直接抓"正在合成的那一帧"：挂在显示的刷屏事件上，把每条已经合成
好的数据抄进画面区画布，再从串口发出去。零额外内存，而且因为它跟在圆角适配回调之后，抓到的
就是肉眼看到的那一屏。

## 具体做法

1. 注册一个显示 `LV_EVENT_FLUSH_START` 回调，**必须注册在板卡自己的圆角适配回调之后** —— 这样
   拿到的是已经做过圆角处理、还没做字节交换的像素。用 `lv_display_get_buf_active(disp)` 加事件
   里的 `area` 拿到这一条和它的 stride，按同样的坐标抄进画布。
2. 只在抓帧时打开拷贝：置标志 → `lv_obj_invalidate(lv_screen_active())` +
   `lv_refr_now(NULL)` 触发一次整屏重画 → 清标志。配 40 行分部缓冲时整屏分成 8 条送来；
   每条渲染完才拷贝，所以画布其余部分仍是旧内容，抓出来自洽。
3. 把画布按原生小端 RGB565 发走（240 × 320 × 2 = 153,600 字节），二进制段期间要关掉控制台的
   LF→CRLF 翻译，发完再恢复。

## 踩过的坑

- **画布式界面不能用 `lv_snapshot`。** `lv_snapshot_take_*` 在找不到顶层对象时会先清空落点缓冲，
  再把控件树画进去。对着画面区画布用，第一次抓回来就是"控件压在黑底上"—— 画面被抹掉了。
  改成"画布可见时抓"也一样：清空之后画布把自己拷给自己，结果还是黑。正确做法是抓刷屏路径，
  不要碰快照 API。
- **整段传输期间必须持 LVGL 锁。** 115200 波特率下这 150KB 要发约 13 秒。中途放锁会抓到撕裂帧：
  用户按一下键，背景会被重新解码进正在读的那块缓冲（我抓到过立绘重影加噪点带）。持锁会让界面
  卡住这十几秒，对调试命令来说是划算的取舍。
- **抓帧任务需要真实的栈。** 在 4KB 的调试图任务里做一次整屏重画会触发 `Stack protection fault`
  并重启设备；同样的工作 8KB 够用。故障看起来像与截图无关的崩溃，直到看清出事任务的名字。
- **字节序由挂钩位置决定。** 端口在 SPI 传输前会交换 RGB565 字节，所以拷贝必须发生在交换之前
  （`FLUSH_START` 正是此时）。放到交换之后就得在主机侧再换回来。
- **代价是一次整屏重画。** 一次抓帧会重新解码背景 JPEG 并整屏合成（本机 130–170ms）；抓完画布里
  留着的是"带文字的整屏"，所以要重画这一幕，让设备状态回到干净。

## 与"静态预留缓冲"方案的分工

[y2lin 的串口截图经验](../y2lin/serial-screenshot-protocol.zh_CN.md) 是静态预留一整块整屏缓冲、
响应 `FAP_SCREENSHOT_V1`。当界面本身没有整屏缓冲、预算也放得下时，那是更合适的做法。
如果界面本来就有一块整屏画布，复用它成本为零，而且抓到的画面不可能与实际上屏的内容漂移。
