# 在无 PSRAM 的板子上打视觉小说剧本包

经验来自[《魔女的夜宴》阅读器](sanoba-witch/README.zh_CN.md)。这个移植要把 5.06 MB 剧本
(101 章、6.1 万节点、112 万字对白)加 107 张背景、292 张 SD 演出图全部放进 Flash,面板是
240 × 320 竖屏,板上没有 PSRAM。过程中踩到三个互不相关的缺陷,但**三者对用户的表现完全相同:
按下「开始阅读」立刻全剧终**。这才是值得写下来的原因 —— 症状掩盖了原因,而让它们现形的那道
启动自检,才是真正可复用的部分。

## 包为什么长这样

剧本存成一个二进制:段表 + 按字频排序的字符表 + 若干名字字典 + 场景表 + 标签表 + 选线规则 +
块表 + 一串独立的 deflate 块。两个决定值得单独说:

- **跳转目标在打包时解析掉。** 源剧本跳的是**标签名**,而同一个名字在不同章节里重复出现;
  打包器把每次跳转解析成 `(场景, 块, 节点)` 三元组存进标签表,固件跳转是 O(1),
  不需要为了找一个标签去解压块。
- **正文存成字符表下标**,不是 UTF-8(每字 2 字节);同一张字符表又是生成字库子集的字形顺序。
  于是字库不可能缺剧本用到的字,16px 4bpp 子集稳定在 3,458 字形 / 456 KB。

实测打包:5.06 MB 节点 JSON → 1.45 MB,单块解压 ≤ 3 KB(记录流 1.99×,对 JSON 3.5×)。

## RAM 决定块大小

块大小不是口味问题。这块板子在应用建完画布、LVGL 内存池和界面之后,堆长这样:

```text
I (1695) main: 空闲堆 15468 字节,最大连续块 7680 字节
```

解压缓冲必须落在**一个**连续块里,而它不到 8 KB —— 所以"一章一块"那种自然的 19.5 KB 块
永远分配不出来。包因此按解压后 3 KB 切块,固件用 4 KB 缓冲;包从 1.28 MB 涨到 1.45 MB,
8 MB Flash 根本不在意。在无 PSRAM 的板子上选块大小,看的是**最大连续空闲块**,不是空闲堆总量。

## 坑一:封装格式,而不是压缩算法

打包器剥掉了 2 字节 zlib 头和 Adler-32,存的是裸 deflate 块。固件的解压路径却是照着同仓库
另一个项目写的 —— 那个项目**保留** zlib 封装 —— 所以调用时带着"解析 zlib 头"的标志。
于是每个块都解不出来,加载器返回 0 字节。

教训不是"该用哪一种" —— 两种都能用 —— 而是**封装属于格式契约的一部分**:在打包器的 spec 里
写清楚一次,让读取端断言它。把裸 deflate 当 zlib 读,结果就是零字节输出,没有任何中间状态可查。

## 坑二:分配失败被当成了"剧情结束"

```c
if (!player_load_chunk(player, scn, player->chunk)) {
    return SANOBA_STEP_STUCK;
}
...
if (!player_step_position(player, scn)) {
    return SANOBA_STEP_ENDING;      /* ← 内存不够也掉到这里 */
}
```

块加载失败有好几种原因:块损坏、表项不对、或者 `malloc` 返回 NULL。加载器对它们一律返回 0,
而状态机把"没有下一块了"直接当成**剧情走完**。于是 32 KB 缓冲撞上 7.7 KB 的最大连续块,
表现就是按下开始阅读的瞬间通关。

把 I/O 与分配失败放在和"内容结束"**不同的返回路径**上,并让日志区分它们。这块板子上,
失败旁边跟一行 `空闲堆 … 最大连续块 …` 通常就足以点名原因。

## 坑三:栈,以及一个"改了却没生效"的配置文件

缓冲修好之后,同样的"立刻结束"又回来了 —— 这次是真的栈溢出:启动自检在 `app_main` 里跑了
一整趟解码(解块 → 解记录 → 分页),溢出默认 3,584 字节的主任务栈。在 `sdkconfig.defaults`
里调大它**没有生效**,因为 ESP-IDF 只在生成 `sdkconfig` 时读这个文件;**已存在的
`sdkconfig` 会保留旧值**,构建仍然按 3,584 字节来。把文件移走让构建重新生成,才拿到想要的值:

```text
#define CONFIG_ESP_MAIN_TASK_STACK_SIZE 8192
```

两点记下来:启动阶段就跑一趟解码,要按它给主任务栈留够(主任务返回后栈会释放,只在启动阶段占内存);
以及当 `sdkconfig.defaults` 的改动没生效时,**去看生成的 `sdkconfig`**,别反复读自己改的那一行。

## 让三个坑现形的启动自检

```c
/* 解出第一个块的第一句,成功就打印数字,失败就打印原因 */
ESP_LOGI(TAG, "剧本包自检:块 0 解压 %u 字节,首句 <%s> %u 字", ...);
ESP_LOGE(TAG, "剧本包自检失败:推进返回 %d,块 0 解压 %u 字节(解压报错: %s);空闲堆 %u,最大块 %u", ...);
```

启动多花几毫秒,却把"游戏立刻结束"变成两种结果之一:带真实数字的通过行,或点名解压器
自己的错误 + 堆状态的失败行。事后回看,封装问题和分配问题都是靠这一行定位的。

## 验行为,不只验像素

串口截图通道(`SANOBAPAGE`)从 LVGL 刷屏路径抓整帧,对版面核查够用。但依赖**状态机与计时器**的
行为 —— 这里指"自动阅读不得调暗、熄屏、休眠" —— 需要一种不动手就进入那个状态的入口。几条小
命令就能覆盖:`SANOBAJUMP <场景> <句>` 拨动阅读进度、`SANOBAAUTO <0|1>` 切换自动阅读,于是
"背光不该变"这件事可以对着日志盯两分钟 —— 背光只在真的变化时才打
`空闲 N ms:背光 恢复/调暗/熄屏`。实测:自动阅读开着 → 135 秒内 0 次背光变化;
关掉 → 60.0 秒记一次调暗。

## 可以直接复用的数字

| 项目 | 实测 |
| --- | --- |
| 剧本 JSON → 包 | 5.06 MB → 1.45 MB |
| 块大小 / 缓冲 | 单块解压 ≤ 3 KB,缓冲 4 KB |
| 开机后堆 | 空闲 15 KB,**最大连续块 7.7 KB** |
| 字库子集 | 3,458 字形,16px 4bpp,456 KB,与字符表同序 |
| 图片包(107 背景 + 292 SD) | 2.97 MB |
| 含两个包的完整固件 | 合并镜像 5.93 MB |
