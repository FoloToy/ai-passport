# 打包素材的名字是打包器与固件之间的契约

本条目来自 **《飞鸟会长不肯认输》**（Asunabi）的发布。那个应用把美术与章节剧本放在一个只读的
flash 分区里读取，而不是编进应用镜像；分区在编译期由一份放在固件之外的源素材生成。

## 查不到的名字是黑屏，不是报错

阅读器会用字符串字面量向素材包查几个名字，例如标题背景 `bg/index_bg.png`。打包器把同一张位图
存成了 `index_bg.png`（收集图片时丢掉了目录前缀），于是查不到。没有任何东西失败：构建全绿、
位图确实在包里（77,824 字节，用包检查器可以看到）、唯一的证据是启动日志里的一行警告。画面
退回到兜底路径，也就是黑色，结果这个版本开机就是黑底标题画面，而那张美术图就在同一个镜像里
几百 KB 之外闲置着。

把固件查的每个名字都当成与打包器之间的契约，并且让失败变得响亮：查不到名字至少应该是编译期或
测试期的错误，而不是"照样能开机"的静默兜底。

## 占位包会掩盖这种不一致

当美术目录缺失时，打包器会产出一个占位包，让不带第三方素材的 clone 依然能配置、构建并启动。
那条路径的名字是对的 —— 它的名字是手写的纯色填充条目。于是名字不一致只在真素材成为默认构建时
才暴露，而真素材正是发布所交付的那种配置。

如果同一条流水线对同一种输出有两套来源（真素材与占位包），要把它们各自与固件比对，而不是只
互相比对。

## 一处声明，一个测试

修法是让打包器的 UI 图片清单直接保存 **pack 名**（同时也是源树下的相对路径），这样名字只有
一处定义，然后把它与固件的查询字面量断言在一起：

- 遍历固件源码里的查询调用（例如 `gal_assets_find(..., "name")`），收集其中的字符串字面量。
- 与打包器的声明对比：固件要查而打包器从不打包的名字、打包了却没人查的 UI 图片，两者都算失败。
- 让这个测试不依赖图像库：把打包器当模块导入（它的图像库是惰性导入的），直接读声明，于是它能
  和其余逻辑一起跑在同一套宿主测试里。
- 把它接进仓库的校验脚本 —— 这才是让 CI 而不是真机测试发现回归的关键。

## 按源素材估算分区

3.0 MiB 的源美术（89 张 PNG）加 30 份 JSON 章节剧本，打包后是 3.55 MiB：约 3.19 MiB 图片负载，
其余是剧本及其文本池。分区是 4 MiB，打包器接收一个上限并在放不下时**让构建失败**，而不是产出
被截断的镜像，因此这两个数字不会悄悄失配。美术在打包时按面板尺寸缩放，而不是按源分辨率存放；
立绘在取 alpha 包围盒之前会先裁到真正能进入屏幕的区域。

## 素材一旦入库，CI 就需要图像库

美术入库之后，每次构建都在打包真实素材，而打包需要 IDF 所用解释器里有图像库（这里是 Pillow）。
工作流里装上它，tag 触发的发布才可信；少了这一步，同一个构建会在打包器这一步变红 —— 至少那是个
响亮的失败，正好与本文开头的问题相反。
