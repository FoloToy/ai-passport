# LVGL 9 的中文位图字体子集

来自 **《沙耶之歌》阅读器**发布（AI Passport 上的横屏视觉小说：44 章、3,828 段对白、3 个结局）。
这些是在这块板子上显示中文的通用经验，不是 fork 私有定制。

> **验证状态。** 下面的数字都来自本次发布的构建产物与实机运行：发布固件内置了
> 16 px / 20 px 两个共 2,839 码位的子集，启动无任何警告，并且完整渲染了全部剧本。
> `lv_font_conv` 的对比是在本机 Node v24 上用同一个 OTF 与同一组参数跑出来的。

## 不要塞一整份中文字库

8 MB Flash、无 PSRAM 的 ESP32-C3 装不下完整中文字体，而且也没必要：应用能显示哪些字符串是已知的。
从两处收集字符集，只栅格化这些字形：

1. 应用自身源码里字符串字面量中的非 ASCII 字符（直接扫 `.c` / `.h`，不要相信注释或口头需求）。
2. 内容本身的全部字符（剧本/章节数据），包括角色名。

两个字号（16 px 正文、20 px「大」字号）合计 2,839 个码位，约占 0.94 MB Flash，不占静态 RAM
—— 因为 LVGL 直接从 Flash 读取字形位图。

## cmap 必须按 LVGL 的查找语义写，而不是按字体文件的

LVGL 的 `get_glyph_dsc_id()` 给每种 cmap 条目赋予了不同含义，所以一份"看起来合法"的 cmap
可能一个字形都查不到：

- `LV_FONT_FMT_TXT_CMAP_FORMAT0_TINY`：连续码位，
  `glyph_id = glyph_id_start + (cp - range_start)`。
- `LV_FONT_FMT_TXT_CMAP_SPARSE_TINY`：在 `unicode_list`（相对 `range_start` 的偏移）里二分查找，
  `glyph_id = glyph_id_start + 命中下标`。
- `LV_FONT_FMT_TXT_CMAP_FORMAT0_FULL`：需要逐码位的 `glyph_id_ofs_list`；
  稀疏字集传 `NULL` 不是"退化成慢查找"，而是直接崩。

由几千个离散码位构成的子集，可用结构是：ASCII 一段 `FORMAT0_TINY` 连续段 + 其余一段
`SPARSE_TINY`；这也正是 LVGL 自带字体的形态。

## 当前 Node.js 下 `lv_font_conv` 写出的位图是坏的

用最后一版（1.5.3，2021）在 Node v24 上跑：同一个 OTF、同一组参数，
加不加 `--no-prefilter` 产出的字节**完全相同**。按 LVGL 的 PLAIN 读法解出来是噪点，
而 LVGL 自带的 Montserrat 字体用同一个解码器完全正常 —— 说明问题不在读取端。
设备上的表现是所有文字整屏乱码，很容易被误判成字体没选中或编码问题。

直接用 Pillow/FreeType 栅格化并自己写 LVGL 位图格式，可以把工具链从信任链里拿掉，
而且结果可以验证而不是靠肉眼：把生成的 C 文件回读、完全按 LVGL 的语义解码每个字形，
再与栅格化结果逐像素比对，任何不一致就让构建失败。

## 几个一定会变成可见 bug 的细节

- **位图打包**：PLAIN（`bitmap_format = 0`）、4bpp、高半字节在前、每个字形起点按字节对齐。
  记错任何一条，整段文字都会错位。
- **行高是排版参数**：`line_height = 像素字号 + 额外行距`，与界面固定的行数预算对齐
  （16 px + 3 = 19 px 行高，一屏 4 行）。若用字体自然行高（Noto Sans SC 在 16 px 时约 24 px），
  每页最后一行会被默默裁掉。
- **空白字符也要有字形**：用全角空格（U+3000）做首行缩进的剧本，必须把它作为
  "空位图 + 全角推进宽度" 编进子集。把它当普通空格剔掉，LVGL 会退回画缺字方框，
  读者看到的就是正文里的一排方块。
- **保留字符清单文件**：把码位清单和字体一起产出；让 `--check` 模式在界面文案或内容更新
  引入了子集未覆盖的字时让门禁失败；并让清单同时作为**输入**，这样从更小的内容变体重生成时
  不会丢掉另一个变体仍在用的字形。
- **源字体不要提交进仓库**（若其许可不允许再分发）。改为在素材文档里记录字族、许可、
  下载来源、重新生成命令与 Flash 影响。
