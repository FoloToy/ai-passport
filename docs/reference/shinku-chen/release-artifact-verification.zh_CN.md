# 静态缓冲按面板算，并验证已发布的产物

经验来自 **四子棋** 的发布：第一版已发布固件启动后只剩 8KB 空闲堆，不得不在社区提交前重做。

## 一个“方便”的常量可能白吃 50KB

该版本新增了串口截图命令（`FAP_SCREENSHOT_V1`），它的帧缓冲必须静态预留：在 LVGL、codec 与 DMA 缓冲都跑起来之后，堆里拿不到 150KB 的连续块。缓冲当时按“两种方向里更大的那个”声明——320 × 320 像素、204,800 字节——而一帧恰好就是面板的像素数：240 × 320 = **153,600 字节，横竖屏相同**。

多出来的 51KB 不会出现在 flash 体积报告里，也不是编译错误。设备上空闲堆从 227KB 掉到 8.3KB、最大连续块 7.7KB，而它照样能启动能玩，所以没有任何显式报错。这类缓冲要按面板几何推导（`BSP_LCD_W * BSP_LCD_H * 2`），而不是拍一个整数；同时给功能加编译开关，方便某个构建把这部分 RAM 还回去。

## 刷你要发布的那个产物，并读启动日志

流程里本来就要求发布后在硬件上验证；可操作的版本是：下载 **已发布** 的合并镜像，从偏移 0 刷入，然后读启动日志里真正重要的数字——逻辑分辨率、任务就绪、空闲堆。这个检查几分钟内就抓到了上面的缓冲问题。

本地复现也必须刷同一个产物，而不是本地构建：同一份源码，CI 构建出来的字节与本地不同。只在本地构建上验证过的修复，并不能证明用户下载到的东西是对的。

如果刚发布的版本有问题、且还没有人消费它，直接替换（删掉 release 与 tag、把 tag 移到修复 commit、让 tag 触发的构建重新发布）比另发一个“只修一个谁都看不见的错”的后续版本更干净。

## 截图命令同时就是封面流水线

有了这个命令，发布封面可以展示设备的真实画面，而不是重绘的示意：从串口抓帧 → 合成进品牌外壳 → 放进场景。封面随后只作为发布元数据（记录文件名与格式），不需要进仓库。
