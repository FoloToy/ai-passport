# LVGL 字符格式陷阱与缺字门禁

在发布 **亚托莉阅读器** 之后整理：该项目的中文界面需要一套 16px 字体子集，覆盖 2,770 个
码位（约 0.39 MB Flash，4bpp，未压缩），来源是剧本资源包加应用自身的界面文案。

## `FORMAT0_FULL` 会让 LVGL 9.6 崩溃，TINY 与 SPARSE_TINY 不会

第一版字体用了最大的排版（`render_mode=FULL`，即稠密的字符描述符表）。编译链接都正常，
字符串也是合法 UTF-8 —— 但设备在第一次绘制中文标签前就崩在字符查找里。把同一份点阵数据
重新生成为：ASCII 用 `FORMAT0_TINY`，其余用 `SPARSE_TINY`（有序码位数组 + 对应索引数组），
行为没有任何变化，崩溃消失。

对任意 CJK 子集来说，稀疏排版本来也更省：位置表只列出真正用到的码位，2,770 个字不需要
一张 20,992 项的稠密表。请把"字符格式"当作移植工作的一部分，而不是生成器的细节 —— 在搭其它
界面之前，先用一条真实的中文字符串在真机上验证它。

## 验证"产出的字体"，而不是"产出字体的工具"

这个项目里所有字体问题都是靠两条便宜检查抓到的：

- **逐像素回读**：生成 C 源码后再解析回来，把每个字的位图与产生它的 FreeType 光栅化结果
  逐点比对。这样生成器的 bug 会让构建失败，而不是在屏幕上显示成糊掉的字。
- **对源码做覆盖检查**：把应用字符串字面量里的所有非 ASCII 字符抽出来，断言它们都在字符
  清单里。以后新增一条带未映射字符的界面文案，会在静态门禁阶段失败 —— 比在真机上发现一个
  方块便宜得多。

字符清单作为文本文件提交，这样门禁阶段不需要字体工具链。

## 生成器经验

- `lv_font_conv` 1.5.3 在较新的 Node.js 下会写出损坏的位图，在设备上表现为满屏噪点。
  一个"出错就大声失败"的仓库内生成器，比把 Node.js 钉死在旧版本更可信。
- 源字体按需要的字重实例化（从可变字体取 `wght=400`），`.ttf` 不进仓库；只提交生成出的
  C 文件与覆盖清单。
- 开机日志里打印 LVGL 内存池用量。同一个项目的"关于"页曾把默认池子耗尽，整屏花掉且重启前
  不恢复；提到 56KB 后正常，而开机日志能在用户遇到之前先把这件事暴露出来。
