# 给「一键一个 ADC」键盘加键位锁

这些结论来自 **Pocket Intercom（随身 AI 对讲机）** 三键控制在真机上的验证（2026-10-01）。属于通用、对上游也有价值的经验：这块板子的三个键共用同一个 ADC 引脚，所以同一硬件上的任何应用都会遇到同一种失效。

> **验证状态。** 在真机 AI Passport 上复现并修复：修复前串口按键日志里能看到误报事件，加上下面的门限后不再出现。触点电平和器件有关；这里的数字来自一台机器，不等于对整批产品的刻画。

## 硬件形态

三个键以电阻阶梯接在同一个 ADC 输入上：每个键接通不同的分压点，所以引脚电压就代表"哪个键被按下"（或"没有键"）。应用层通过 BSP 拿到 `PRESS` / `HOLD` / `RELEASE` 一类事件，底层是先做电压窗口判定、再映射成键。

由此立刻得到两个推论：

- 同时按两个键会得到一个不属于任何窗口的电压；这个输入本质上就是"一次只能一个键"。
- 因为判定依据是电压比较，**任何**让电平发生变化的原因 —— 不只是真实按下 —— 都可能被读成另一个键。

## 失效方式：长按却被报成别的键

按住某个键时，触点并不是完全稳定的：电平会瞬时漂移或瞬断，读数就可能落进**相邻键**的窗口里。结果正是那种第一眼不太敢信的现象：**按住 OK，设备却像是被按了 UP。**

观察记录：

- 与**按压时长**相关，而与触点干净程度关系不大：极短按几乎不会遇到，长按偶尔会遇到。所以它出现在用长按的功能里（设置、快进），而普通菜单翻页看起来一切正常。
- 单张截图、或时间点不巧的单行日志都看不出来；需要带时间戳的按键事件日志才能看到那次跳变。
- 任何把"某个键已经按下时又来一个 key-down"当成真实用户意图的代码，都会照这个误报行动。

## 修法：按住期间锁住键位

两处小改动，都放在 BSP 而不是各个应用里：

1. **键位锁。** 一旦接受了某次 key-down，就忽略后续的 key-down，直到该键上报 release。输入本身就约定"一次一个键"，所以这是顺着硬件而不是对抗它。
2. **显式门限。** 短按与长按门限显式配置（这里是 180 ms 与 500 ms），不依赖默认值，这样每个应用对"一次按压算什么"的判定一致，也便于在测试里推理。

两者到位后，长按就是长按，相邻键不会再因为触点噪声被触发。

## 让它变得可查的诊断手段

- 留一个串口「按键黑匣子」：记录每次原始电平变化的时间戳、映射到的键、以及最终接受的事件。误报跳变在这份日志里一目了然，在别处几乎看不见。
- 同时记录被键位锁**丢弃**的事件。紧挨着一次合法 release 之前出现的丢弃事件，就是这个失效的特征；它同时也说明键位锁正在起作用。
- 不要靠"把电压窗口放宽"来解决：窗口本来就是按阶梯尺寸定的，放宽只是把问题挪到相邻键的边界上，并没有消除。

## 可以照抄的

- 键位锁与按压门限放进 BSP，让每个应用都自动继承；各应用自己去做 debounce 一定会漂移、互相不一致。
- 在 API 契约里就写明"一次一个键"，并在头文件里讲清楚，应用代码才不会去设计硬件根本报不出来的双键手势。
- 提供一个能开关的按键事件日志；它决定了你面对的是"这按键有点飘"还是一行修复。

显式的短按 / 长按门限也作为 BSP 改动提交到了上游，这样别的应用不必各自再推导一遍同样的时序。
