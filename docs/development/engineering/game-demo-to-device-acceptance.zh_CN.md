# 游戏 Demo 到真机验收 SOP

选择先在浏览器试玩的游戏可以使用这套流程：把可移植 C 编译成 WebAssembly（Wasm），通过 HTML/CSS/JavaScript（H5）外壳调顺玩法与交互，再验收对应固件的真机表现。这是项目集成方式；模板并未提供通用的 Wasm 游戏构建器或硬件模拟器。

每个验收阶段留下证据后再进入下一阶段。小范围真机可行性探针可以提前进行，尤其是新增渲染器、音频链路或内存方案时。将测量结果反馈到 Demo 设计中；这些探针不能代替最终真机验收。

## 0. 定义验收契约

开发前，在游戏任务文档中写一张简短的场景表：开始/结束状态、屏幕方向、实体 UP/DOWN/OK 键及其位置、短按/长按、正常/失败路径、重玩/退出，以及玩家必须读懂的线索。对照实际设备确认映射，不要默认画面中的左/右就对应物理 UP/DOWN。对重要的帧节奏、内存余量和按键响应，事先定义可测的真机目标，并写明场景和采样时长。标明哪些场景需要关闭调试提示游玩，哪些允许使用受控场景。

| 案例 | 初始条件与操作 | 预期结果 | 验收证据 |
| --- | --- | --- | --- |
| 开始与暂停 | 从标题页开始，进入游戏再暂停 | 每次按键只触发一次动作；运动停止；下一步操作明确 | 输入测试与可见试玩 |
| 结果与重玩 | 到达成功或失败状态，再重新开始 | 结果保持显示，直到执行约定动作；重玩重置预期状态 | 受控场景与玩家完整游玩 |
| 输入中断 | 取消触控、隐藏标签页，或松开长按键 | 不持续误行走，也不额外触发短按 | 浏览器输入测试；物理时序单独验收 |

按实际游戏替换或补充这些示例。无尽玩法应定义有代表性的一段游玩及其重置/退出条件，无需虚构通关状态。

**通过条件：** 不看源码的玩家也能说清每一步要判断什么、按哪个键。操作或通关规则仍有歧义时，回到玩法设计，不进入固件实现。

## 1. 用一份可移植 C 代码和 H5 评审外壳实现 Demo

把玩法状态机、时钟与 tick 规则、行走、碰撞和计分放在可移植 C 代码中，让同一批源文件用于主机测试、Wasm 和固件。渲染器可移植时一并共用；基于 LVGL 的页面也可以只共用玩法模型与布局数据。ESP-IDF/LVGL、ADC 按键、电量、显示传输与任务所有权放在设备适配层。浏览器输入、显示、缩放与评审控件留在 H5 外壳，不再实现第二套计分或行走模型。

项目需要提供一层薄桥接，支持初始化/重置、输入事件、时间步进、状态读取，以及适用时的共享渲染输出。原生 C 和 Wasm 统一时间单位、随机种子、缓冲区所有权与输入顺序。在项目指南中记录所选编译器/SDK 版本及可复现的构建、测试、HTTP 启动命令。通过 HTTP 加载 Wasm，加载失败时显示明确错误，调试场景与普通玩家流程隔离。

每款游戏提供一个独立 Demo 页面，不额外加入跨游戏导航。明确说明网页对应用退出动作的映射（例如返回当前游戏标题页）；这一边界仅是预览便利，不代表固件导航已经通过验收。

模拟按键要对应约定的实体按键，并覆盖浏览器原始按下/松开及长按时序。将原始事件归一化为 BSP 支持的动作（PRESS、CLICK、DOUBLE、LONG）；浏览器松开事件不代表要求设备新增松开回调。以选定的设备方向和原生像素尺寸作为构图基准。CSS 可以缩放画面；网页独有的平滑处理或动画不能掩盖游戏缺帧，也不能改变相机运动。素材、字体和界面文字应能追溯到候选固件。为共享源码和生成产物记录哈希，过期时让项目检查失败；仅重新生成 manifest 不等于重新构建。

**通过条件：** 浏览器全新加载时运行的是当前 C 构建。用同一随机种子、输入事件和时间步进序列回放原生 C 与 Wasm，比较状态与共享渲染输出，差异在记录的容差内。单独实现的浏览器 UI 应标明仅作视觉参考：核心一致性不能验证对应 LVGL 页面、字体选择和重绘生命周期。

## 2. 先验收可玩的 Demo

运行玩法逻辑、输入、渲染和 C/Wasm 一致性测试。然后用画面上可见的 H5 操作做两轮互补验收：

1. **受控场景：** 覆盖各个成功/失败分支，适用时覆盖暂停/继续、操作中断、返回开头和重玩。对难以自然到达的状态使用场景注入，并保存注入条件与预期结果。
2. **无提示游玩：** 不打开揭示答案的控件，从头到尾按预期路线玩一遍。观察关键线索能否发现、按键是否可预期、转弯后能否辨认方向、切换时是否出现莫名黑帧或站位跳变、通关和失败反馈是否明确。

以选定设备方向的原生分辨率和常见桌面/手机窗口检查开头与结果界面、文字可读性、HUD 与场景同步、动画连续性，以及失焦和取消输入后的行为。根据结果修改 C、素材或 H5 外壳，并重复受影响的检查，直到指定玩家/评审者认可交互，记录评审人、候选版本和日期。只通过场景注入不能代替正常游玩；单张截图也不能证明动画舒适。

**通过条件：** 场景表中的完整流程和边界案例都有 PASS 证据，C/Wasm 一致性结果是当前版本，且记录玩家认为 Demo 手感可以进入真机的结论。未解决的问题应明确列出，不能悄悄带入真机关卡。

## 3. 安全构建并安装真机候选版

按 [AI 开发指南](../ai-guide.zh_CN.md)，通过 `main/` 生命周期与 BSP 接口，将已验收的 C 核心集成进应用自己的 UI。在要求的 ESP-IDF 环境下运行[仓库完整验证](build-and-test.zh_CN.md)。依据该指南验证候选版实际的镜像偏移、应用大小和分区布局，不把某个游戏的分区选择变成模板通用要求。记录提交号、源码是否有未提交变更、Wasm manifest、固件哈希及共享素材哈希。按构建指南保留匹配的构建与调试产物。

安装前取得刷写授权，并识别实际板卡和串口。按照构建指南，选择兼容当前布局与数据保留需求的安装方式。回读原固件不是前置条件。检测到设备不等于取得刷写或整片擦除授权；保留用户需要的数据，并遵守项目特定的受保护区域要求。传输成功和正常开机仅证明安装成功，不等于玩法验收。

**通过条件：** 已验证的候选版能进入预期起始画面，实际安装布局符合批准的方案，并且能识别实际安装的是哪一版。

## 4. 在物理设备上验收

用实体按键重复同一张场景表。至少完成一次正常游玩或约定的无尽玩法时段，再针对罕见分支做受控检查。核对初始文字及字形、短按/长按、运动、结果/重玩、退出再进入，以及该游戏特有的场景。显示电量时，分别检查读数可用、不可用时占位、迟到读数刷新；不要求首帧虚构百分比。检查实际重绘、任务清理，以及使用音频时的音效表现。将实际屏幕和手感与已验收 H5 基准比较，记录差异。

在有代表性的场景测量设备独有事实：提交帧率及可获得时的屏幕完成帧节奏、渲染和显示耗时、空闲/最低堆内存与最大连续块、按键响应、崩溃、看门狗、分配失败、撕裂或黑帧。按游戏探针计划预热并采样足够时长，只比较相同场景，使用第 0 关预先定义的目标。网页性能计数、串口截图和 C 自动化测试都不能证明实体屏幕的流畅度或长时间游玩的内存安全性。

**通过条件：** 实体按键和完整流程通过、真机测量达到目标，没有让游戏难以理解或不舒服的未解决差异。若修复修改了共享 C 或素材，应重新构建 Wasm 与固件、复测受影响的 Demo 场景，再复测真机；不能仅凭网页结果关闭真机失败项。

## 留存交接记录

每个候选版保留一份简短记录：

| 字段 | 必需证据 |
| --- | --- |
| 版本身份 | 提交号、Wasm manifest/源码哈希、固件与素材哈希、板卡版本、安装方式 |
| Demo | 场景表、受控场景结果、无提示游玩记录、画面/动画证据、原生 C/Wasm 一致性 |
| 构建 | 静态/主机测试、固件及所配置布局的检查结果 |
| 真机 | 安装版本证明、实体完整游玩及边界案例、性能/内存采样、脱敏日志或截图 |
| 结论 | Build、Host tests、Demo、Device tests 分别标 `PASS`、`FAIL` 或 `NOT RUN`；负责人、日期、`Unverified` 项目 |

缺少证据时标 `NOT RUN`。不要把设备身份信息或未脱敏串口数据提交进仓库。必要关卡为 `FAIL` 或 `NOT RUN` 时，不标记为可发布。

## 命令与交接清单

每个游戏需要自行提供 Wasm 构建、产物过期检查、一致性测试和 HTTP 预览命令，并在浏览器验收前执行。候选版准备好后，在项目根目录使用已有仓库检查：

```bash
./tools/validate.sh --static
# 运行完整检查前先激活要求的 ESP-IDF 环境。
./tools/validate.sh
```

交给真机测试者前，提供 Demo 地址/启动命令、场景表和 Demo 验收结论、已验证固件的准确标识、安装/数据保留方案、真机测量计划。适用的板卡检查参见[硬件指南](../../hardware-design/AI_HARDWARE_DEVELOPMENT_GUIDE.zh_CN.md)。网页 Demo、固件构建与真机验收分别记录结果。
