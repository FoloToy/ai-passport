# 应用 Demo 到真机验收 SOP

本流程适用于先在浏览器中评审可移植 C 逻辑和交互、再完成真机验收的应用，包括计时器、阅读器、外设控制界面和游戏。将共享 C 编译成 WebAssembly（Wasm），以 HTML/CSS/JavaScript（H5）提供评审界面。硬件相关功能使用明确的测试输入或适配层；浏览器结果只验证其中实际表达的行为。

项目开发者准备候选版本和证据，指定评审者验收交互，真机测试者验证已安装的候选版本。按以下关卡推进并记录结果。必要时提前进行小规模真机可行性探测，将测量结果反馈到预览与资源检查中；最终真机验收仍然必需。

本文件定义验收方法。上游基础仓库不提供统一的 Wasm 构建器、硬件模拟器或应用负载模拟器。应用专用的构建器、夹具、负载模型、阈值和命令应留在应用的 Fork 或分支，并在那里说明。

## 0. 定义验收约定

实现前编写场景表，明确进入和退出状态、屏幕方向、实体 UP/DOWN/OK 的位置、支持的按键动作、正常和错误路径、取消、重试及重新进入。在实际设备上确认映射；画面的左右方向不能直接代表实体键位。针对相关负载定义可测量的响应、更新节奏和内存目标，注明预热和采样时长。

| 示例 | 准备与输入 | 预期结果 | 证据 |
| --- | --- | --- | --- |
| 计时器 | 开始、暂停、继续，直至完成 | 时间和反馈符合约定 | 确定性时钟测试与正常用户操作 |
| 阅读器 | 打开内容、翻页、退出，再次打开 | 阅读位置和显示内容符合保留策略 | 内容夹具、交互评审及真机显示 |
| 外设界面 | 注入延迟或不可用读数，再恢复 | 加载和错误状态清楚，新数据能替换旧状态 | 适配层测试，再验证真实外设 |
| 输入中断 | 取消触摸、隐藏页面，或长按后松开 | 没有持续动作或误触发短按 | 浏览器输入测试与实体按键时序 |

用应用真实场景替换这些示例。区分需要受控夹具的场景与必须正常完整操作的场景。持续运行的应用应定义有代表性的会话及停止、重置条件。

**通过条件：** 评审者能够说明每一步的操作和可观察结果。先解决交互或完成条件的歧义，再将 Demo 用作固件参考。

## 1. 共享可移植 C 逻辑，使用 H5 评审界面

将可测试的状态转换、时间规则、计算和协议放在可移植 C 中，同一份源码用于主机测试、Wasm 和固件。渲染与布局计算可移植时也应共享；LVGL 页面可以只共享应用模型。设备适配层负责 ESP-IDF/LVGL 集成、硬件 I/O、显示传输及任务。H5 负责浏览器输入、展示和评审控制，不重复实现应用状态机。

定义薄桥接层，支持初始化和重置、输入事件、时间步进、外部事件注入、状态查看及适用的共享渲染输出。各目标统一单位、事件顺序、缓冲区所有权，以及使用随机数时的种子。列出电量、传感器、网络响应、存储等模拟来源及尚未表达的行为。夹具响应不能证明外设、无线或持久化行为。

每款应用提供一个独立 Demo 页面，跨应用导航放在页面之外。说明浏览器对应用退出动作的特殊映射，例如返回应用入口画面。这只是预览便利；固件导航仍需真机验收。

将浏览器按下、松开及长按时序映射到应用使用的 BSP 动作 PRESS、CLICK、DOUBLE、LONG。浏览器松开不构成新增设备回调的要求。按选定方向和原生像素尺寸评审；CSS 可以放大画面，但不能掩盖缺失更新或改变动画时序。素材、字体和文案应能追溯到固件。

记录可复现的构建、产物过期检查、一致性测试、HTTP 预览命令及编译器和 SDK 版本。通过 HTTP 加载 Wasm，并明确显示加载失败。为共享源码和生成产物记录哈希，产物过期时让项目检查失败；更新清单本身不等于重新构建。调试夹具不进入正常用户流程。

**通过条件：** 浏览器全新加载时运行当前 C 构建。向原生 C 和 Wasm 回放相同输入、外部事件及时间步进，在约定容差内比较状态与共享输出。单独实现的浏览器 UI 应标为视觉参考；模型一致不能验证对应的 LVGL 页面、字体或重绘生命周期。

## 2. 在 Demo 中验收交互

运行适用的主机逻辑、输入、渲染及 C/Wasm 一致性测试，再通过可见控件完成两类操作：

1. **受控验证：** 覆盖完成、错误、取消、重试、适用的暂停和继续、退出及重新进入。为难以触达的状态保留夹具和预期结果。
2. **正常用户验证：** 不借助调试工具完成预定任务，检查信息是否容易发现、按键是否可预期、衔接是否连续、成功或失败是否明确。游戏应包含没有异常或答案提示的正常游玩，其他应用执行自己的日常用户任务。

按需检查入口、加载、内容、错误及完成状态，覆盖原生分辨率和有代表性的桌面、移动端视口。检查文字可读性、状态标识与实际状态是否同步、动画连续性及失焦和取消行为。记录评审者、候选版本、日期和未解决问题。仅通过夹具不能代替正常操作；静态图片不能证明动画舒适度。

**通过条件：** 必需场景与一致性检查通过，指定评审者认可交互可以进入硬件阶段。持续调整共享 C、素材或展示，直至满足条件。

## 3. 验收资源和调度压力

Wasm 在宿主运行时中执行可移植应用逻辑。浏览器 CPU 限速和帧率上限无法复现 ESP32 调度、DMA、总线、内存分配或外设时序。例如，显示忙等可能阻止音频或传感器服务任务按时执行，而浏览器交互仍然流畅。

按应用风险选择检查：持续音频、频繁显示更新、采样、通信突发、存储停顿或明显的内存分配负载。测试前定义限值。不适用的检查记录 `NOT APPLICABLE` 并说明原因；缺少测量应记为 `NOT RUN`，不能因此豁免。应用参数和负载适配器放在应用 Fork 或分支中，适用时复用共同模型。可选的[通用资源工具](resource-stress.zh_CN.md)提供周期与缓冲任务及回归样例；它不是强制的设备性能关卡，也不加入上游仓库统一验证脚本。

1. **采集负载：** 在当前共享 C/Wasm 构建中回放有代表性的操作和外部事件；仅设备可执行的路径可使用另有说明的可执行测试环境。记录真实状态变化与服务需求，覆盖启动、稳定工作、空闲、失败、清理和重新进入。保留输入、源码与构建哈希，说明模拟延迟会反馈到应用状态，还是仅对固定轨迹估算资源需求。
2. **用真机测量校准：** 测量相关 CPU 工作、阻塞或忙等、任务优先级、传输和服务间隔、有效缓冲余量、空闲及最低堆内存、最大连续块。记录设备、固件身份、场景、预热、时长、方法、假设和不确定性。桌面执行时间不是设备 CPU 时间，刷新总耗时不是纯总线耗时，标称缓冲容量不是实测有效余量。用独立真机样本对照预测并记录差异。
3. **运行正反例：** 候选配置必须满足既定限值。注入相关故障，例如 CPU 停顿、忙等、数据延迟、消费者变慢、缓冲不足或过量分配。每个反例必须因预期原因失败。负载模型不执行分配失败恢复和清理时，应另行覆盖。始终通过的测试不能支持验收。
4. **明确校准缺口：** 合成数据或部分测量输入可用于回归测试和探索性估算，不能获得已校准性能 `PASS`。要求校准的关卡在证据不足时必须失败或保持 `NOT RUN`。共享 C、适配层、缓冲、优先级或传输行为变化后，应更新受影响的负载、测量和检查。

在结果旁说明模型边界：调度与抢占假设、初始缓冲状态、延迟反馈、未建模的中断、驱动和缓存影响、堆碎片，以及适用的真实输出质量。内存估算使用一致基线，不重复计算已有分配。不得将应用专用参数当作统一板卡默认值。本地压力结果不能认证真机验收通过。

**通过条件：** 适用限值通过，反例能检测注入故障，所需校准有测量支持，未解决的模型与真机差异明确阻塞验收。保留精确输入、命令和工具版本、哈希及报告，使其他开发者能够复现。

## 4. 构建并安装真机候选版本

遵循 [AI 开发指南](../ai-guide.zh_CN.md)，通过 `main/` 和 BSP 接口将已验收核心接入应用自己的 UI 与生命周期。在要求的 ESP-IDF 环境中运行[完整仓库检查](build-and-test.zh_CN.md)，验证候选版本的实际镜像偏移、大小及分区布局。记录提交和未提交源码状态、Wasm 与源码和素材哈希、固件身份，按构建指南保留匹配的调试产物。

获得刷写授权，确认设备和串口，并按[刷写与存储数据政策](firmware-layout.zh_CN.md#烧录与已存数据)选择安装方式。检测到设备不代表授权刷写或整片擦除。无需将原固件读回备份作为前提。保留用户所需数据并遵守应用布局。上传或启动成功只证明安装完成，不能证明应用已验收。

**通过条件：** 获批候选版本启动到预期入口，布局符合安装方案，且能够识别实际安装的构建。

## 5. 真机验收

使用实体按键重跑场景表，至少完成一次正常用户任务或约定的持续会话，并受控验证少见情况。检查字形、按键时序、状态反馈、重绘、退出和重新进入、任务清理。显示电量时，覆盖可用、不可用及延迟读数。按应用实际使用情况验证真实外设、持久化、网络、音频和电源切换，对照已验收预览的画面与交互并记录差异。

在有代表性的持续负载下测量相关设备目标：输入和服务延迟、提交帧及可观察的面板完成节奏、CPU 和传输耗时、空闲及最低堆内存、最大连续块。检查崩溃、看门狗、分配失败、过期数据、音频断供、撕裂和黑帧。使用第 0 关约定的负载、预热及采样时长。浏览器计数器、串口截图和主机测试本身不能证明这些设备属性。

**通过条件：** 必需实体场景和实测目标通过，不存在妨碍正确或舒适使用的未解决差异。修改共享逻辑或素材后，重建 Wasm 与固件，重跑受影响的 Demo 检查，再复测真机。浏览器通过不能关闭真机失败项。

## 记录交接

| 字段 | 证据 |
| --- | --- |
| 身份 | 提交及源码状态、Wasm 与源码和素材哈希、固件哈希、板卡版本、安装方式 |
| Demo | 场景表、夹具、正常用户操作、一致性与画面和动画证据、评审者及决定 |
| 资源压力 | 适用风险和限值、精确负载与配置和工具身份、校准及假设、正反例、模型与真机差异 |
| 构建 | 仓库与主机检查、固件构建和配置布局验证、匹配的调试产物 |
| 真机 | 已安装构建身份、实体场景、外设及性能和内存测量、脱敏证据 |
| 决策 | 分别记录 Build、Host tests、Demo、Resource stress、Device tests；负责人、日期和 `Unverified` 项 |

使用 `PASS`、`FAIL`、`NOT RUN`；只有不在应用适用范围内的可选检查才使用附理由的 `NOT APPLICABLE`。私密设备身份和未脱敏日志不进入提交记录。必需关卡失败或缺少证据时，不得宣布已经就绪。

每款应用记录自己的预览和资源检查命令，交接前执行，再运行仓库命令：

```bash
./tools/validate.sh --static
# 运行完整检查前，激活要求的 ESP-IDF 环境。
./tools/validate.sh
```

向真机测试者交付预览 URL 和启动命令、已认可的场景及未解决问题、资源证据、精确的已验证固件身份、安装与数据方案及测量计划。适用板卡检查参照[硬件指南](../../hardware-design/AI_HARDWARE_DEVELOPMENT_GUIDE.zh_CN.md)。
